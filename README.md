# Проектирование высоконагруженного аналога 2ГИС
## 1. Тема и целевая аудитория
### 1.1 Описание сервиса
«2ГИС» - российская цифровая экосистема со справочником городов, картой,
навигатором и другими полезными опциями. Сервис помогает находить нужные места,
строить маршруты, ориентироваться в городе и принимать решения на ходу.

### 1.2 Целевая аудитория
- Количество пользователей в месяц(**MAU**): 60 млн за второй квартал 2025 [1](https://www.similarweb.com/ru/website/2gis.ru/#overview)
- Количество пользователей в день(**DAU**): 20 млн за первый квартал 2024 [1](https://www.similarweb.com/ru/website/2gis.ru/#overview)
- Географическое положение: Азербайджан,
                            Армения,
                            Беларусь,
                            Грузия,
                            Казахстан,
                            Кыргызстан,
                            Россия,
                            Узбекистан.

### 1.3 Ключевой функционал сервиса
- Просмотр карточки организации (адрес, телефон, график работы, рейтинг, фото, отзывы)
- Просмотр зданий, входов и этажей
- Поддержка тематических слоёв карты (трафик, транспорт, парковки, велодорожки и др.)
- Инкрементальное обновление скачанных карт

### 1.4 Ключевые продуктовые решения
- Геопоиск рядом с пользователем
- Поиск организаций по названию, категории и ключевым словам
- Скачивание карт регионов для оффлайн-использования
- Оффлайн-поиск и оффлайн-маршрутизация

### Сетевой трафик
k = Peak / Average
Пиковый час составляет примерно 8.4% суточного трафика. [9](https://www.precisiontrafficsafety.com/solutions/traffic-studies/)
Cредняя часовая нагрузка равна 1/24 ≈ 4.17%.
k = 8.4/4.17 ≈ 2.0
При расчёте используется коэффициент суточной неравномерности **k = 2** для определения пиковой нагрузки.

# 3. Глобальная балансировка нагрузки

## 3.1 Функциональное разбиение по доменам

Для разделения разных типов нагрузки сервис разбивается на несколько доменов:

- `tiles.2gis.ru` — тайлы карты  
- `api.2gis.ru` — поиск и карточки организаций  
- `route.2gis.ru` — построение маршрутов  
- `cdn.2gis.ru` — офлайн-карты и статические файлы  
- `2gis.ru` — основной сайт  

Такое разделение позволяет независимо масштабировать карту, API и систему доставки файлов.

---

## 3.2 Размещение дата-центра

![alt text](image.png)

По данным Similarweb около **95.6% трафика 2ГИС приходится на Россию**.

Поэтому основной дата-центр размещается в **Москве**, так как это позволяет минимизировать задержку для основной аудитории сервиса и использовать развитую телеком-инфраструктуру региона.

---

## 3.3 Схема балансировки

Для глобальной балансировки используется **Geo-Based DNS**.

Geo-Based DNS направляет пользователя в ближайший регион обслуживания на этапе DNS-запроса.  
Этот механизм подходит для сервисов с серверным API (поиск, карточки организаций, маршруты).

Принцип работы:

1. Пользователь делает DNS-запрос к домену сервиса  
2. DNS определяет регион пользователя по IP  
3. Пользователю возвращается адрес ближайшего узла обслуживания

# 4. Локальная балансировка нагрузки

В качестве локального балансировщика выбирается **L7-балансировщик NGINX**.  
Он подходит для 2ГИС, потому что позволяет выполнять **SSL termination**, маршрутизацию HTTP-запросов, кэширование и сжатие ответов. Кэширование на уровне NGINX снижает нагрузку на backend-сервисы и ускоряет отдачу часто запрашиваемых данных.

В качестве стратегии балансировки используется **round robin**, так как запросы к API, поиску, карточкам организаций и тайлам можно равномерно распределять между одинаковыми backend-узлами.

## 4.1 Схема локальной балансировки

Схема обработки запросов внутри дата-центра:

`L7 NGINX → application servers`

Где:
- **NGINX** принимает HTTPS-запросы от клиента
- выполняет **SSL termination**
- при необходимости отдает кэшируемые ответы
- перенаправляет запросы на backend-сервисы:
  - `api`
  - `search`
  - `route`
  - `tiles`
---

## 4.2 Обеспечение отказоустойчивости

Для отказоустойчивости используется схема резервирования **N+1**.
Формула резервирования:

**N+1**, где:
- **N** — минимальное количество балансировщиков, необходимое для обработки пиковой нагрузки
- **+1** — резервный узел на случай отказа одного балансировщика

При отказе одного узла трафик продолжает обслуживаться оставшимися балансировщиками без остановки сервиса.

Дополнительно отказоустойчивость обеспечивается за счёт:
1. **health checks** — NGINX направляет трафик только на доступные backend-узлы  
2. **горизонтального масштабирования** — при росте нагрузки можно добавить новые экземпляры балансировщика  
3. **распределения запросов между несколькими backend-серверами** — отказ одного приложения не останавливает весь сервис

---

## 4.3 Расчёт количества балансировщиков

Из расчётов нагрузки выше:
- **Peak RPS** ≈ **13 086 rps**
- **Peak traffic** ≈ **102.6 Gbit/s**

### Ограничение по SSL termination

По тестам NGINX основное L7-прокси способно обрабатывать высокий объём HTTPS-трафика; для нашей нагрузки в **13 тыс. rps** ограничение по SSL termination не является критичным.
Следовательно, в данном проекте узким местом становится не CPU на SSL, а **пропускная способность сети**.

### Ограничение по сети

Примем допустимую полезную нагрузку на один L7-балансировщик:
**25 Gbit/s на сервер**
Тогда минимальное количество балансировщиков:
**N = 102.6 / 25 ≈ 4.1**
Округляем вверх:
**N = 5**
С учётом резервирования **N+1**:
**5 + 1 = 6 балансировщиков**

## 4.4 Итог

Для локальной балансировки нагрузки в 2ГИС используется **NGINX L7** с алгоритмом **round robin**.  
Минимально требуется **5 балансировщиков** по ограничению сетевой пропускной способности.  
С учётом схемы резервирования **N+1** итоговая конфигурация составляет:
**6 L7-балансировщиков NGINX**
